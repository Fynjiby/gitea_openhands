# Gitea по HTTPS (доступ по IP, самоподписанный сертификат)

TLS терминирует сам Gitea, обратного прокси нет. Сертификат самоподписанный,
потому что Let's Encrypt не выдаёт сертификаты на голый IP. Значит, клиенты
(браузеры и git) будут считать его недоверенным, пока он не добавлен в
их доверенные хранилища — об этом раздел «Доверие к сертификату».

Настраивать руками ничего не нужно: IP вводится один раз, скрипт сам кладёт
его в `.env` и в сертификат, а compose собирает из него ссылки и клон-URL.

Файлы в папке:

| Файл | Назначение |
|---|---|
| `docker-compose.yml` | сам сервис; IP и порты берёт из `.env` |
| `make-cert.sh` | создаёт `.env` и сертификат, проверяет конфиг |
| `.env.example` | шаблон `.env` (создаётся только при первом запуске) |
| `README.md` | этот файл |
| `.gitignore` | исключает данные, ключи и `.env` из git |

## Первый запуск

На сервере, в папке с этими файлами:

```sh
chmod +x make-cert.sh              # если файл скопирован с Windows
sudo ./make-cert.sh 203.0.113.10   # <- ваш реальный IP сервера
docker compose up -d
docker compose logs -f gitea
```

`make-cert.sh` нужно запускать **от root** (`sudo`): он выставляет владельца
файлов на uid 1000, под которым работает контейнер, — иначе Gitea не сможет
прочитать приватный ключ и не стартует.

Что скрипт делает и что проверяет:

| Действие | Зачем |
|---|---|
| проверяет, что аргумент — корректный IPv4 | опечатка вроде `203.0.113` ловится сразу, а не на клиентах |
| записывает `SERVER_IP=` в `.env` | один источник правды для compose |
| создаёт `certs/server.crt` и `certs/server.key` с IP в SAN | без SAN в виде `IP Address:...` браузер не примет сертификат |
| сохраняет существующий сертификат, если он ещё годен и покрывает этот IP | повторный запуск не ломает доверие на клиентах |
| делает ключ читаемым для uid 1000, режим 640 | контейнер не работает от root |
| проверяет `docker compose config` | ошибка в конфиге видна до запуска |

Ожидаемый финальный вывод:

```
SERVER_IP=203.0.113.10 written to .env
subject=CN = 203.0.113.10
X509v3 Subject Alternative Name:
    IP Address:203.0.113.10
  docker compose config: OK
```

Открыть: `https://203.0.113.10:3001/` (порт меняется через `WEB_PORT` в `.env`).
Браузер покажет предупреждение — это ожидаемо до тех пор, пока сертификат
не добавлен в доверенные.

**Файрвол.** Должен быть открыт TCP-порт веб-интерфейса (`3001` по умолчанию)
и порт SSH (`2223`):

```sh
sudo ufw allow 3001/tcp
sudo ufw allow 2223/tcp
```

## Проверка, что всё работает

```sh
docker ps --filter name=gitea-ip          # STATUS должен стать (healthy)
curl -k https://127.0.0.1:3001/api/healthz   # {"status":"pass"}
openssl s_client -connect 203.0.113.10:3001 -servername 203.0.113.10 </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -ext subjectAltName
```

Проверка имени хоста (сертификат выписан именно на этот IP):

```sh
curl --cacert server.pem https://203.0.113.10:3001/api/healthz
```

`server.pem` — копия `certs/server.crt`, см. ниже.

## Доверие к сертификату на клиентах

Скопируйте публичную часть сертификата с сервера на машину клиента —
приватный ключ (`server.key`) не покидает сервер никогда:

```sh
scp user@203.0.113.10:/path/to/gitea/certs/server.crt ./gitea-server.crt
```

**Windows, Chrome / Edge / системное хранилище.** Двойной клик по
`gitea-server.crt` → «Установить сертификат» → «Локальный компьютер» →
«Поместить все сертификаты в следующее хранилище» → «Доверенные корневые
центры сертификации» → Готово. Перезапустить браузер.

**Firefox** использует своё хранилище: Настройки → Приватность и защита →
Сертификаты → «Просмотр сертификатов» → вкладка «Центры сертификации» →
«Импортировать» → выбрать `gitea-server.crt` → отметить «Доверять при
идентификации веб-сайтов».

**git.** Указать сертификат только для этого хоста (не меняя глобальные
настройки):

```sh
git config --global http."https://203.0.113.10:3001/".sslCAInfo /путь/к/gitea-server.crt
```

Файл должен быть в формате PEM — `.crt` от `openssl req` уже в нём.
Проверка:

```sh
git ls-remote https://203.0.113.10:3001/user/repo.git
```

**curl:**

```sh
curl --cacert /путь/к/gitea-server.crt https://203.0.113.10:3001/api/healthz
```

Если хотите, чтобы `git` и `curl` доверяли без флагов, добавьте
`gitea-server.crt` в системное хранилище ОС — тогда `http.sslCAInfo` не нужен.

## SSH

SSH не зависит от TLS и работает как обычно, сертификат ему не нужен:

```sh
ssh://git@203.0.113.10:2223/user/repo.git
```

## Продление и смена IP

Сертификат живёт 825 дней. За месяц до истечения или при смене IP — та же
команда с новым адресом, затем перезапуск:

```sh
sudo ./make-cert.sh 198.51.100.7
docker compose restart gitea
```

Скрипт сам определит, что старый сертификат больше не подходит, и пересоздаст
пару. После смены IP сертификат нужно заново добавить в доверенные на клиентах
и обновить путь в `http."https://<ip>:<port>/".sslCAInfo` у git.

Что НЕ удаляется при этом: данные в `gitea-ip/data/` (репозитории, база,
пользователи) остаются нетронутыми.

## Если что-то не поднимается

| Симптом в `docker compose logs gitea` | Причина и решение |
|---|---|
| `SERVER_IP is not set` | не запускался `make-cert.sh`, или `.env` лежит не рядом с `docker-compose.yml` |
| `permission denied` на `server.key` | скрипт запускали без `sudo`: `sudo ./make-cert.sh <тот же ip>` |
| `tls: failed to find any PEM data` / `no such file` | нет `certs/`, или папку `certs` не смонтировали (проверьте `volumes`) |
| контейнер `healthy`, но снаружи не открывается | закрыт порт в файрволе/у облачного провайдера |
| браузер: `certificate is not valid for <ip>` | IP в сертификате ≠ IP, по которому заходят; перегенерируйте с нужным |
| браузер: `NET::ERR_CERT_AUTHORITY_INVALID` | нормально, пока сертификат не добавлен в доверенные |

## Если появится домен

Тогда самоподпись больше не нужна: направьте A-запись на сервер и замените
самоподписанный сертификат на выпущенный Let's Encrypt — либо через `certbot`
и те же `CERT_FILE`/`KEY_FILE`, либо поставив вперёд Caddy и вернув Gitea
на `GITEA__server__PROTOCOL: http` внутри docker-сети.
